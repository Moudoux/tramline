## Probe view

**Asked for by the user on 2026-11-05: a live view of the head during the tram check and during the mesh probing (`G29 P1`). Plan steps 1 and 2, the tram check, built 2026-11-05 for the GUI, `go test` and headless Chrome on the simulator only, see Built: tram check. Steps 3 and 4, the mesh's progress and its view, built later on 2026-11-05, the same way, see Built: mesh. Steps 5 and 6 prepared 2026-11-06: `tramline mesh` reads the heights, and the first and last mesh point are logged, `go test` and headless Chrome on the simulator only, see Built: mesh heights. Both need the printer next, see Proposed printer tests.** For the GUI, and the read-only page too if the user agrees, see Desktop GUI and Web page. The GUI polls, it doesn't push, see How requests reach the Pi. A one-second poll suits probing, which takes 2 to 5 seconds a point.

### What's known

- **Tram check:** Tramline drives it, so the server knows every step. `G28`, then `G30` at front-left, front-right, back-right, back-left, at X/Y 25 and 205 (see Tram check, "Probe points are 25 and 205"), then park at Z30 over X115 Y115. `TramJob` already has `Step` as text and `Rounds[].Readings` with each corner's X, Y and Z as it arrives. Real times: `G28` 14 to 20 s, each `G30` about 5 s. **The extra move after each probe:** the head moves on by the probe's offset, about 41.5 mm left and 7 mm forward, see Tram check. The view should show that, or at least not contradict it.
- **Mesh, from a real stream, `test-logs/2026-11-04-stream/t8-long/server.log`:** `Mesh invalidated. Probing mesh.`, then `Probing mesh point N/25.` for N = 1 to 25, 2.3 to 3 s apart, then a position report, `X:66.50 Y:212.00`. **No height is reported per point.** The 26 matching lines in each stream log show it happens on every print. `C29` gives the grid: 5×5 between 25 and 205 (see Tram check, the `C29` row).
- **The order of the mesh points isn't reported.** UBL probes the nearest unprobed point to the head, not row by row, so point N's position has to come from copying that rule, starting from the position before `G29`, here `X:156.50 Y:122.00` nozzle. Probe or nozzle coordinates, and the offset, need care. Check the result against the LCD or a video before trusting it.
- **The copied order fits the real log, 2026-11-05.** Marlin's rule (`find_closest_mesh_point_of_type`): the next point is the unprobed one with the least distance from where the *probe* was before `G29` (X115 Y115), plus a tenth of its distance from the nozzle now. From nozzle X156.5 Y122 it gives the middle first and back-left (25, 205) last, and the real `G29` ended with the nozzle at X66.50 Y212.00, which is the probe on (25, 205). Each line comes as a point starts, before the head moves there, and each gap matches the travel this order gives: 45 mm moves 2.30 s, 90 mm 2.55 s, 135 mm 2.78 to 2.85 s, 180 mm 3.00 s, timed by the longer axis's distance, as a diagonal of 45 by 45 takes the same as 45 straight. A fit of 1.66 s probing plus a move at up to 180 mm/s with 460 mm/s² gives every gap to within about 0.05 s. That's strong evidence, though not a sight of the head: a video beside the GUI would settle it.
- **Unknown:** whether these messages reach the Pi during a print from the card. Which command prints the heights is settled from the source, 2026-11-06: `M420 V1 T1`, see Mesh under Firmware findings, but it hasn't run on the printer. `G29 W` printed nothing, see Tram check, and the source says why.
- **Not available:** `AUTOREPORT_POS`, and `M114` can't be sent during a stream. So, like the print view, positions are worked out, not measured.

### Plan

1. **Tram, server:** add to `TramJob` a structured target, for instance `phase` (homing, moving, probing, parking) and `target: {x, y}`, set as each command goes. Keep `Step` as it is for the CLI. Make the simulator's `G28` and `G30` take realistic times so the view can be seen.
2. **Tram, view:** in `shared/view.js`, markers at the four probe points. The head glides to the target at a plausible speed, and the probe drops. Each reading becomes a pin, scaled up so 0.05 mm shows, coloured by distance from the average. The verdict and knob advice as in the GUI now. A print's own tram check (`PrintJob.Check`, the `checking` state) should use the same view.
3. **Mesh, server:** in a stream, parse `Probing mesh point N/M.` into the print job, for instance `mesh: {point, of, started_at}`, with a test from the real log's lines. Expose it in `WebStatus` only if the user agrees to the page showing it.
4. **Mesh, view:** a 5×5 grid of points over the bed, filling in as N rises, and the head at point N by the copied UBL order, marked as an estimate.
5. **Mesh heights, needs the printer:** with the user's OK, printer on, nothing moving, try `G29 T` and `M420 V` and record the output in Firmware findings. If one works, `tram info` and a "Show mesh" button can draw it as a coloured surface. Adding it to every print's stream after `G29 P1` changes the print, so that's the user's decision.
6. **SD prints:** check in the log of a real SD print whether the messages arrive. If not, the mesh view is for streams only.

### Built: tram check

Steps 1 and 2, 2026-11-05. Not installed on the Pi, and not seen with the real printer.

- **Server:** `TramJob` in `internal/server/tram.go` has `phase` (`homing`, `probing`, `parking`), `target` and `step_seconds`, set by `tramStep` as each command starts and cleared when the run ends, so the history file doesn't get them. `target` is `{corner, x, y}` for probing, the point the **probe** touches, and `{x: 115, y: 115, z: 30}` for parking, where the **nozzle** stops (`marlin.ParkXY`, `marlin.ParkZ`, exported for this). `step_seconds` is how long the phase has run by the server's clock when status was read, so the browser times the motion without its clock having to agree with the Pi's. `step` stays as text for the CLI. A print's own check uses the same `TramJob`, so it gets the same view. Test: `TestStatusGivesPhaseAndTarget`.
- **Only in `GET /v1/status`,** not in the read-only page's `/status`, whose `WebStatus` still only has `tramming`. Putting it on the page is the user's decision. The GUI polls `/v1/status` every 2 seconds during a check, as before, and the view fills the gaps from `step_seconds`.
- **Simulator:** `sim.Options.HomeDelay`. `serve --sim` now takes 17 s for `G28` and 5 s for each `G30`, against 0.5 s before, so `sim-gui.sh` and `sim-web.sh` take about 40 s longer before a print. Go tests keep their own short `MoveDelay`.
- **View, `TramScript` and `TramScene` in `internal/webui/shared/view.js`:** the head is drawn as the nozzle plus the probe, 41.5 mm left and 7 mm in front (`M851`), joined by a bar. Each phase is a script of timed moves at this printer's figures: homing goes to X0, Y0, then puts the probe over the middle (nozzle X156.5 Y122, as seen before `G29`) and probes Z twice. Probing travels at Z6 with the probe over the point, lets the pin down, descends at 8 mm/s (`C851` S480) to nozzle Z0.9, lifts, then moves the nozzle onto the point, the extra move from Tram check. Parking lifts to Z30 at 10 mm/s and moves at 50 mm/s. The scripts come to about 4.7 s a corner, against 4.8 to 5.4 s measured, and about 14 s for homing, against 14 to 20 s, after which the head waits for the server's next phase. The drawn head follows its script with a 0.12 s lag, so a late poll doesn't make it jump.
- **Readings:** rings at the four probe points, grey, orange while being probed, and coloured once read. Each reading is a pin standing from its point, with the round's average at 30 mm and 20 mm for every 0.05 mm away from it, a faint plane at the average, and a label with the value. Until a round finishes it's measured from the average so far, then from the round's own `relative_mm`. Colour is the distance from the average against half the limit: green to half of that, amber, then red. On a fail, the corner to change is red with "lower" or "raise" on its label.
- **When the GUI shows it** (`showTramView` in `gui.js`): while a check runs, for 2 minutes after one ended that the tab saw running, and while a print is `adjusting`, but never once a print is starting, running or cancelling. The camera looks at the whole bed meanwhile, unless the user has moved it, and goes back to the print after.
- **Also fixed:** the Printer tab's bed map threw "round.readings is not iterable" for the few seconds before a round's first reading, as Go sends `null` then, which also stopped the rest of that status update. And the status card now gives the check's step during a print's check, such as "Tram check: homing.", instead of a fixed sentence.

**Tested in headless Chrome on the simulator, 2026-11-05,** driven over DevTools as in Desktop GUI, with screenshots every 1.3 s: a check from the Printer tab (homing, all four corners, the park, pins and labels, the finished view), a print's check that fails (`--fail-tram`: back-right red, "lower" on its label, the print's ghost on the bed, the head parked), a print's check that passes and hands over to the print (tram view gone, camera on the print, head following the file), and a 420 px wide window, where the labels stay inside the view. No script errors. The print in these runs was started from the GUI's own dialog, see the warning below.

**Not proven:** anything with the real printer. Whether the scripts' timings match it (a video of a check beside the GUI would show it), whether polling every 2 s feels smooth enough, and a real browser rather than headless Chrome. Also `repeat` over 1 in the view.

**Warning, 2026-11-05:** while testing this, a print meant for the simulator went to the real printer, which started heating before the user stopped it. The script read the simulator's throwaway config folder from `sim-gui.sh`'s output after a fixed wait, got an empty string, and with `XDG_CONFIG_HOME` empty the client used the real login. **When testing on the simulator, start prints from the simulator GUI's own dialog, after checking `full.simulated` is true, or use `${CFG:?}` and check the path is under `/tmp` before any client command.**

It passed in the two builds before it and the two after, and nothing it runs was changed.

### Built: mesh

Steps 3 and 4, 2026-11-05. Not installed on the Pi, and not seen with the real printer.

- **Link:** `Probing mesh point N/M.` lines now go to the server's `PrinterLine`, as halts and "Done printing" did, for a stream or from the card. `marlin.ParseMeshPoint` reads them, in `internal/marlin/mesh.go`. **`PrinterLine` took any other line as a halt,** so mesh lines return before that, in any state, or a stray one would fail the print.
- **Server:** `PrintJob.Mesh` is `{point, of, started_at, point_at}`, set only while the job is `running`. Point 1, or a count going back, starts a new mesh. It's replaced, not changed, as copies of the job share it. The job isn't saved for each point. `GET /v1/status` adds `point_seconds`, how long ago the point started by the server's clock, as `step_seconds` does for the tram check. **Not in the read-only page's `/status`**, as that's the user's decision. `tramline status` adds "Probing the mesh, point N of 25" while it goes.
- **Simulator:** `G29 P1` prints "Mesh invalidated. Probing mesh.", then a line for each point in the copied order, taking 1.66 s plus the fitted travel, 2.28 to 3.05 s a point, then the position, X66.50 Y212.00. `sim.Options.MeshScale`: 1 in `serve --sim`, the real pace, about a minute; 0 in Go tests unless set. `G29 A` answers "Unified Bed Leveling System v1.01 active" as the real one did. `G29 W` and others still answer as before. The order and timing are in `internal/sim/mesh.go`.
- **View, `meshOrder`, `meshScript` and `MeshScene` in `internal/webui/shared/view.js`:** the same order and timing as the simulator's, copied, so **keep the two in step**. 25 rings over the bed: grey to come, orange for the current one, blue once probed. Blue, not green, as no height is known. The head travels at Z6 with the probe over the point, lets the pin down, descends to the bed, lifts, pins up, which adds up to 1.66 s. A label over the current point says "point N of 25, estimated", and the status card says "Probing the mesh, point N of 25. The head's place is an estimate, as the printer doesn't report it." Between polls the view moves on to the next point when the estimate says it's due, but never more than one ahead, so a stopped `G29` doesn't run on. It draws through the tram view's renderer, which comes first if both are given.
- **When the GUI shows it** (`meshShown` in `gui.js`): while the print is `running` and its mesh's latest point is under 30 s old, until 6 s after the last point. Then the camera goes back to the print. The full status, which has the mesh, is read every 2 s while it shows, and while a running print is still within its first 4096 bytes, to catch it starting.
- **Tests:** `TestParseMeshPoint`, `TestMeshOrderMatchesTheRealPrinter` (the order's last point and every gap from the real log, within 0.1 s), `TestMeshPointsFromARealStream` (the real lines with their real times, through `PrinterLine` to `/v1/status`), `TestG29InAStreamReportsItsMesh` (a file with `G29 P1` through the simulated firmware and the link), and `TestMeshLineBeforeTheFileIsIgnored`.

**Tested in headless Chrome on the simulator, 2026-11-05,** with `./sim-gui.sh --port 18790 --minutes 3 test-logs/2026-11-03-print/test-tile_PETG.gcode`, the print started from the GUI's own dialog after the script checked `full.simulated` was true and the page was on 127.0.0.1. The JS order matched the Go order exactly. The simulated `G29` took 58.4 s from point 1 to point 25, against 58.7 s on the real printer. Screenshots every 1.4 s showed the points filling in, the head over the current point, all 25 blue with the head at back-left at the end, and the view handing back to the print with the camera on it. No script errors.

**Installed** on the Pi 2026-11-05, `dev-20261105221625`, confirmed by `status`. Not yet run with the real printer.

### Built: mesh heights

Prepared 2026-11-06 for steps 5 and 6, build `dev-20261106102839` in `dist/`. **Installed 2026-11-06, committed later that day. `tramline mesh` after power-on has run on the real printer, see Proposed printer tests. The SD print and a print's fresh mesh haven't.**

- **Which command:** `M420 V1 T1`, the only one sent, as it only prints in this firmware's source, see Mesh under Firmware findings. `G29 T1` prints the same but is the command that probes, so it isn't used.
- **`tramline mesh [--raw] [--json]`, `GET /v1/mesh`:** a separate read-only command, built like `tram info`, with the same guards in a shared `askPrinter`: refused during a print, a tram check or a copy, while a stream's stray heaters are being turned off, with the plug off or the printer not connected, and while an SD print runs. Nothing moves. `marlin.MeshInfo` sends `marlin.MeshCommand` through `link.Exchange` with the 10 s idle limit. `marlin.ParseMeshReport` reads the CSV map into `z[row][column]`, row 0 at the front, `null` for `NAN`, and "valid", the slot and whether levelling is on. The reply comes back raw too, and a reply it can't read isn't an error, just `parse_error`, so the first real output is always kept. The CLI prints the grid as seen from the front, back row at the top, with the range, and a reminder of which mesh it is.
- **GUI:** "Read the mesh" beside "Ask the printer" under More, showing the same grid as text. `GET /v1/mesh` is added to the GUI's allowed routes. **The coloured surface isn't built,** as you said only if heights come back: that waits for the first real reply.
- **Which mesh it reads:** after power-on, the one loaded from EEPROM slot 0 at boot, last saved who knows when. Just after a print, until the plug is cut, that print's own `G29 P1` mesh. A read then doesn't stop the auto-off (only `keepPowerOn` does) and doesn't change the print. So the fresh mesh can be read with no change to prints, in the minutes while the nozzle cools below 50°C, by hand. Doing it automatically at each print's end is a small change, and your decision, like reading it during the print.
- **Logging for step 6:** `meshPoint` logs "print N: probing the mesh, point 1 of 25, sd" (or `stream`) at a new mesh's first point, and "print N: mesh probed, point 25 of 25, 58.4s after the first" at the last. The other points still aren't logged.
- **Why the old SD logs don't answer step 6:** the stand print (4 h 10 min, from the card, 2026-11-04) logged no mesh lines, but during a card print the server's `M27` is waiting behind `G29`, so the lines would have arrived inside that wait, which kept them without logging. The installed build passes mesh lines to the server before the wait sees them. In the firmware, an ordinary `SERIAL_ECHOLNPGM` goes to the only serial port whatever the command's source, so the lines are expected to arrive, but that's a reading, not a sighting.
- **Simulator:** keeps a mesh: a tilted "stored" one at power-on, and after `G29 P1` the same with a dip in the middle, so the two can be told apart. Answers `M420` as the source does. `G29 A` turns its levelling flag on. Its card print still only times the print and doesn't run the file, so it can't show mesh lines during an SD print.
- **Tests:** `TestParseMeshReport`, from the format worked out of the source, `TestMeshInfoOnlyAsksForTheMap` (only `M420 V1 T1` sent, the stored mesh read back), `TestMeshInfo` in the server (front row first, an unreadable reply kept raw, refused with the plug off), and `TestMeshLinesDuringAnM27WaitReachTheServer`, for step 6.

**Tested in headless Chrome on the simulator, 2026-11-06,** `./sim-gui.sh --port 18791 --minutes 2 test-logs/2026-11-03-print/test-tile_PETG.gcode`, the driver stopping unless the page was on 127.0.0.1 and `simulated` was true, the print started from the GUI's own dialog: "Read the mesh" after power-on gave the stored mesh, valid, slot 0, levelling off. During the print it was refused, "A print is running". Right after the print, with the plug still on, it gave the print's mesh with the dip, levelling on. After the cut, "The plug is off". The log had the first and last point, 58.4 s apart. No script errors, only the two expected 409 replies.

### Built: mesh surface and the read after each print

2026-11-06, after the printer tests, as the user asked ("do what you recommend"). Build `dev-20261106105922`, `go test` and headless Chrome on the simulator only. **Not installed. Not yet run on the real printer.**

- **Read after each print, the recommendation the user accepted:** `autoOff` calls `readPrintMesh` once, right after it turns the heaters off and before it waits for the nozzle to cool, holding the operation lock. It reads only if the job's own `G29` reached its last point (`job.Mesh.Point == Of`), the job finished or was cancelled (not failed, as a halted board answers nothing), it wasn't started elsewhere, and the printer is connected. Without its own mesh, a read would only give the stored mesh, so there's none. One `M420 V1 T1`, 30 s limit. The result, or why it failed, goes in the print job as `mesh_read` (`read_at`, `mesh`, `error`), saved with the job, and as a line in `mesh-history.jsonl` in the data folder, with the print's ID, name and route, as the journal doesn't survive a reboot. The log says "print N: mesh after the print, range X mm". Nothing is sent during a print, so prints are unchanged. Only prints Tramline started get it, as only they get the auto-off.
- **Surface, `HeightsScene` in `shared/view.js`:** the 5×5 heights as a surface over the bed, blended linearly between points as UBL does, in 6×6 steps a cell, from the tram pins' base and scale: 30 mm at the mesh's average, 20 mm for every 0.05 mm away. Coloured from grey at the average to blue below and orange above, full at ±0.1 mm, a fixed scale so meshes compare by eye. A pin, ring and label with the height at each point, and the faint plane at the average. Points with no height get a grey ring and no surface around them. Drawn with its own shader, colour per corner, slightly see-through. A tram check or a mesh being probed comes first, and the camera looks at the bed while it shows.
- **GUI:** "Read the mesh" draws the reply as well as the text. "Hide the mesh" removes it. Under More, "The mesh after <file>, read at <time>: range X mm" with "Show it", from `mesh_read` in the full status. A reading under 10 minutes old shows by itself once per print, and anything from heating to cancelling clears it, so it never covers a print under way.
- **Tests:** `TestG29InAStreamReportsItsMesh` now also waits for the read after the print (one `M420 V1 T1`, the simulator's probed mesh with its dip, the history line), and `TestNoMeshReadWithoutTheFilesOwnMesh` checks a file with no `G29` gets no read.
- **Headless Chrome on the simulator, 2026-11-06,** the same guarded driver, the print started from the GUI's own dialog: the stored mesh as a surface after power-on, `mesh_read` in status within a second of the print finishing, before the plug cut 6 s later, the line and button under More, the surface shown by itself once, and again after a page reload. No script errors, only the two expected 409s.

**Notes for steps 5 and 6, written before starting them:**

- **Step 5, where the mesh is:** Tramline cuts the plug after every print, so after power-on the firmware's mesh is whatever it loads at boot, perhaps the one saved in EEPROM, not the last print's. So a read after power-on shows the stored mesh, if any, and only a read soon after a `G29 P1`, with the printer still on, shows a fresh one. Check what `M503` or the boot lines say about a loaded mesh before reading anything into it.
- **Step 5, how to send it:** Tramline has no raw-command route, by design. `TramInfo` in `internal/marlin/motion.go` sends a fixed list of commands that don't move anything, through `link.Exchange` with a 10 s idle limit, and `tram info` prints the replies. The smallest change is adding `G29 T` and `M420 V` to that list, or a separate `mesh info` the same way. Both should only print. Confirm that in Marlin's source for this build (MRiscoC Professional Firmware, based on bugfix-2.1.x, Dec 2023) before sending them. `M420` with `S` or `Z` changes things, so send only `V`.
- **Step 6, how to tell:** during a print from the card, `tramline status` says "Probing the mesh, point N of 25" while the lines arrive, and the GUI shows the grid. The server doesn't log each mesh line, so check status every few seconds during the first minutes, or add a log line for the first and last point in `meshPoint` first.
